- The test layers, outermost-in: Journey ▸ System ▸ Component ▸ Adapter ▸ Use-case ▸ Domain (+ a shared Port-contract suite). Coverage labels are one per layer — `src`, `domain`, `use-case`, `adapter`, `component`, `system`, `journey` — no aggregating or aliasing.
- **Use-case is to Component as Journey is to System.** Two orientations — behaviour-oriented (Use-case, Journey) and system-oriented (Component, System) — across two realism tiers. The cheap tier doubles what it can (Use-case wires in-memory twins; Component keeps the real adapters and doubles only the external edge — an in-memory database, stubbed outbound HTTP) and so is always written and exhaustive. The real tier integrates everything affordable (real infrastructure) and so is selective. Use-case and Component carry exhaustive coverage; System and Journey validate the same surfaces with real everything, selectively.
- Journey tests are the outermost, max-realism functional layer and the outside-in entry point: the whole app wired with real driving and driven adapters across a multi-capability user arc that establishes the contexts it touches, passes representative error paths (not every one), and eventually succeeds. Name them `*.journey.test.*` under `test/journey/`. Keep the journey curated and runnable in under 5 minutes — trim to the highest-impact and most-recent steps; there is rarely more than one or a few, never one per capability.
- System tests validate a single capability against real infrastructure — the same surface a Component test covers, proven for real. Selective, not exhaustive: spend the expense on the highest-impact capabilities and expand over time. Name them `*.system.test.*` under `test/system/`.
- Component tests wire the whole app for one capability with real driving and driven adapters, doubling externals only at the edge — an in-memory database and stubbed outbound HTTP. They run in-process, need no external services, and carry exhaustive single-capability behaviour coverage — the assembled wiring the Use-case twins skip, proven without paying for real infrastructure. Name them `*.component.test.*` under `test/component/`.
- Adapter tests at the Adapter layer exercise one adapter against its port contract. For driven adapters, that means real infrastructure — Testcontainers, a local service, or recorded cassettes. Not mocks. This is `adapter` coverage (it replaces the old overloaded "integration").
- Driven adapters ship in two flavours that share one port contract suite: an in-memory twin used by Use-case tests, and a real adapter used in production, at the Adapter layer, and at the System layer. Both adapter test files import and run the same `*.contract.ts` suite. The real adapter's test file layers on adapter-specific behaviour (timeouts, retries, constraint handling) beyond the shared suite.
- The default at every layer is real external dependencies wherever the layer calls for them. Any mock or stub must carry a visible marker naming the reason — at Journey and System because the fallback breaks max-realism, at Component because it changes which edge is doubled, at Adapter because it breaks the real-downstream contract. Silent mocking is never acceptable.
- *Do not* use environment variables to vary behaviour between test and runtime.
